# ADR-003 — Scope lokasi: pivot `location_user` + global scope + Policy

| Item | Detail |
| ---- | ------ |
| Status | Disetujui (simulasi architect). Berlaku saat PR T0.02 di-merge oleh Salman. |
| Tanggal | 6 November 2026 |
| Terkait | Architecture §9; task T0.02 |

## Konteks
Setiap data transaksional milik satu lokasi; user hanya boleh melihat lokasinya (R-01, S-06). Sistem dirancang multi-lokasi sejak awal.

## Opsi
1. Pivot `location_user` + global scope Eloquent + Policy
2. Fitur *teams* spatie/laravel-permission
3. Skema/database terpisah per lokasi

## Keputusan
Pivot `location_user`, trait `BelongsToLocation` dengan `LocationScope`, dan Policy per model. Data di luar lokasi user menghasilkan 404. Bypass hanya lewat `withoutLocationScope()` yang eksplisit dan diaudit saat code review (AR-07).

## Konsekuensi
+ Tidak terikat fitur teams; mudah diuji dua arah.
+ Query terfilter otomatis, mengurangi risiko lupa filter.
- Job queue dan command harus membawa konteks lokasi eksplisit (diuji di T1.02).

## Pembaruan 6 November 2026 — hasil review keamanan T1.02 (R4)
Review independen menemukan lima celah laten; semuanya ditutup sebelum merge dan dibuktikan dengan test serta uji mutasi.

| Temuan | Keputusan |
| ------ | --------- |
| F1 `location_id` tidak divalidasi ketat: PHP `(int)"1_0"` = 1, tetapi PostgreSQL 16+ membaca `'1_0'::bigint` = 10 | Semua `location_id` lewat `LocationWriteGuard::normalize()`: hanya int positif atau string `^[1-9][0-9]{0,17}$`; nilai yang diperiksa ditulis ulang sebagai int sehingga sama dengan yang dikirim ke database |
| F2 Job async menerima lokasi apa pun (worker tidak punya `Auth`) | Lokasi diperiksa saat **dispatch** (`CapturesLocationActor::bindLocation`), ID pemicu disimpan, dan `RunsInLocation` memeriksa ulang akses pemicu saat job berjalan (akses yang dicabut atau user yang dihapus = ditolak) |
| F3 Penulisan gagal terbuka tanpa konteks/principal tak dikenal | Penulisan tanpa konteks melempar `MissingLocationContext`. Proses sistem harus eksplisit lewat `LocationContext::asSystem()` (hanya console). Principal login yang bukan `HasLocationAccess` ditolak; guest di request HTTP tidak boleh memakai konteks. **Syarat: principal API (mis. token POS) wajib mengimplementasi `HasLocationAccess`.** |
| F4 `location_id` bisa dipindah lewat jalur tanpa event (`saveQuietly`, `insert`, `upsert`, `update` massal, SQL mentah) | Pengaman dipindah ke `performInsert/performUpdate` dan `LocationScopedBuilder` (insert/upsert/update massal), ditambah **trigger database** `prevent_location_id_change` yang dipasang per tabel lewat `LocationGuard::attach()` |
| F5 `Location::$guarded = []` membuka `cutover_at` dan `is_active` | `$fillable` eksplisit; `cutover_at` hanya lewat Action `SetLocationCutover`; `Model::preventSilentlyDiscardingAttributes()` aktif di luar produksi |

### Aturan untuk tabel transaksional baru
1. Model memakai `BelongsToLocation`.
2. Migration memanggil `LocationGuard::attach('<tabel>')` di `up()` dan `LocationGuard::detach('<tabel>')` di `down()`.
3. Jangan menulis tabel ber-lokasi lewat `DB::table(...)->insert()` mentah: lewat model atau `Model::query()->insert()`.

### Batas yang diketahui
- SQL/`DB::table()` mentah untuk **insert** tidak bisa dijaga database (tidak tahu konteks user); larangannya lewat code review. Update `location_id` tetap ditolak trigger.
- `Location` sengaja tidak ber-scope sehingga semua user bisa membacanya; Policy `Location` ditutup di T1.04 (ISS-014).
